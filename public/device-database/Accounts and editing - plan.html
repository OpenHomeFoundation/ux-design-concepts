Planning · Stage 03

Accounts and editing: a database the community keeps

A reference is only as current as the people who tend it. Stage 03 lets community members sign in, edit a device page, and have that edit attributed and reviewed before it goes live. The trick is doing it without spending Foundation's two guarantees: reading stays free and account-free, and the reported core stays read-only. This is the plan for the editing core, and the children that build on it.

Builds on Stage 02 · Richer device pages · holds the line set by the editorial stance

Editing is added at the edges, never at the centre. Sign-in gates writing, never reading. An edit touches the contributor fields, never the reported verdict. And nothing a contributor submits is live until it has been reviewed, as a pull request, with their name on it. Stage 03 makes the database maintainable by adding a careful write path around a record that stays exactly as trustworthy as it was in Foundation.

The two guarantees it must not spend

Open to read, careful to write

Stage 03 introduces accounts, which is precisely the moment a reference site usually starts asking visitors to sign in and starts letting anyone overwrite anything. Foundation's guarantees forbid both. They are restated here as the constraints the whole stage is built around.

Reading stays freeno account wall

Sign-in unlocks editing and a few personal surfaces. It never gates a lookup. A signed-out visitor reads every page in full, exactly as in Foundation.

The core stays read-onlycontributor fields only

An edit changes the curated and reported-context fields. The local-or-cloud verdict and the reported record are not hand-editable, so editing cannot quietly rewrite the headline fact.

Drafts make this safe to live with. An in-progress edit overlays the approved record and autosaves to your account, so leaving and coming back keeps the work, and a pending field is locked so two people do not fight over it. The approved record underneath never changes until review says so.

The write path

Draft, submit, review, attribute

Every change walks the same path, and the path is the product. A contributor edits into a draft, submits it, which opens a pull request, and the change goes live only when that request is merged. Decline is a first class outcome, not a dead end: a declined edit can be revised and resubmitted. Every step carries the contributor's name.

Putting review on a pull request is the load-bearing decision. It means the edit history is real and external, attribution is a GitHub identity rather than a name we mint, and the conversation about a change lives in one place every contributor can see. The edit history on a device page is the merged tail of that same record.

The path

A core that defines the stage, then four children

The core is sign-in, the edit mode, the draft and submit flow, and the attributed edit history. Ship it and Stage 03 exists. Each child builds on that core and on nothing else, so each can be switched off on its own. No child depends on another, which is the test that keeps them children and not a tangle.

Where we draw the line

Community-kept, editorially held

Sign-in never gates reading. Accounts exist for editing and a few personal views. The lookup stays open to everyone, the Foundation promise that does not bend.

Nothing goes live unreviewed. Every edit is a pull request first. The approved record a reader sees never changes on a single contributor's say-so.

Every change is attributed. Edits carry their author through submission, history, and the device page. Anonymous-to-read, named-to-edit: the reporting population stays private, the editors do not.

The reported core is not hand-editable. Contributors improve the curated and contextual fields. The verdict and the reported record keep their own provenance, untouched by the edit form.

Recommendation

What to hold, in order

  1. Guard the read path above all. Any feature that would put a lookup behind sign-in is out, no matter how convenient. The open read is why the database is trusted.

  2. Keep review external and attributed. The pull-request model gives real history and real identity. Do not replace it with an in-house approval queue that only we can see.

  3. Keep the four children independent. Profiles, notifications, Your edits, and trusted sources each depend only on the core. If one starts needing another, the seam has broken.

  4. Hold the editable surface to contributor fields. The day the verdict becomes a free-text edit, the headline fact stops being reported and starts being opinion.
