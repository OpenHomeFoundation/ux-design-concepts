Planning · Stage 03 increment

Appearance: the same database, lit the way your eyes want it

The theme engine already runs. A boot script resolves light or dark before the first paint, and every token flips cleanly, so the whole site is already dark-mode ready. What is missing is the human control. This increment adds an Appearance tab to Settings: choose Light, Dark, or follow your system, sharpen contrast per mode, and tune a few display and behavior options. This is the plan for that, the grouping, and the lines that keep it small.

Builds on Stage 03 · Accounts and editing · engine in tokens.css · tab in community-edit-pages.jsx

The machinery exists. This is the dial. Dark mode is not a rebuild, it is a token layer that already adapts. Appearance gives a person the switch for it, a contrast layer on top, and a few small toggles for display and behavior. It changes how the database is lit and how it behaves, never what it says. Each preference applies the instant you pick it, saved to your account so it follows you to every browser and device you sign in on.

What it is

Theme mode: System, Light, or Dark

Three preview cards, the macOS and GitHub idiom: each shows a miniature of the database in that palette, so you choose by sight rather than by reading a label. System is the default and follows the operating system live, so a person who never opens this tab still gets dark mode at night if their machine does. Its card is split, light on one side and dark on the other, to say as much at a glance. Light and Dark are explicit overrides that hold regardless of the system. The choice writes to data-resolved-theme on the page, the same attribute the boot script already sets, so the existing dark tokens apply with no new code path.

There is no Save button. Like the security actions on the next tab, the setting is discrete: it applies and writes to your account the moment you choose it, so the change is live the instant you see it.

What it is

Contrast: a master switch, then one per mode

Increase contrast is one switch that, when on, reveals two nested switches: Light mode and Dark mode. Each nested switch decides whether the high-contrast palette applies while that mode is the active one. So a person who keeps Theme on System can ask for higher contrast in dark only, and get the normal palette by day and the sharper one at night, with no further fuss.

High contrast is implemented the same way dark mode is: a data-contrast="high" layer that overrides a handful of existing tokens. Hairline borders step to --border-strong, muted text moves closer to full --fg, and the focus ring thickens. No element gets a new color, the quiet ones simply get louder.

How it is organized

Three groups, by what each control changes

Theme picks the mode. Display fine-tunes how that mode renders: contrast per mode, and dimming device photos so they do not glare on dark. Behavior covers interaction: reduced motion, and whether a hovercard previews a link before you open it. Each group answers a different question, so no control sits where you would not look for it.

Appearance, or Accessibility?

We chose Appearance, and declined text size

Fair flag, reduce motion reads like an accessibility control, because it is one. But standing up an Accessibility menu for one or two toggles is worse than no menu, it reads as a promise of an accessibility story the rest of the product has not built yet. So the cheap controls ride along in Appearance, where the machinery already sits: reduce motion, dim device photos, and show hovercards join Theme and Contrast. Text size is the one we decline, because it forces a real rem audit and genuinely wants an Accessibility home we are not opening yet.

Where we draw the line

A reading preference, not a paint set

Per account, so it follows you. Appearance saves to your profile, so the database looks the same on your laptop, your phone, and any browser you sign in on. A signed-out visitor still gets the full control, held locally until they sign in, and that same local value doubles as a pre-paint cache so a signed-in return visit never flashes the wrong theme before the account preference loads.

System is the honest default. Until a person says otherwise, we follow the operating system and keep following it live. We do not guess, and we do not pick dark to look modern.

One accent, no color picker. The single Braun-orange is signal, it marks active, recording, and error. A custom accent would turn signal into decoration and is exactly the thing this design system refuses. Appearance dials light, contrast, and behavior, never hue.

Everything applies instantly. No Save button anywhere on this tab. Each control is discrete, so the page is the preview.

Recommendation

What to hold

  1. Ship five controls in three groups. Theme, then Display (contrast per mode, dim device photos), then Behavior (reduce motion, show hovercards). Theme and contrast are the same token-override trick, so pages adapt for free, and the rest ride a media query, one filter rule, and the existing hovercard component. None of it is expensive.

  2. Save to the account, cache to the device. The preference lives on the profile so it follows a person across browsers and devices, with a local copy that resolves the theme before first paint so a return visit never flashes. Default to System and track the OS live for anyone who never touches it.

  3. Decline text size, and do not open an Accessibility menu yet. Reduce motion is cheap and render-level, so it rides along in Appearance. Text size is the control that forces a rem audit and genuinely wants an Accessibility home. Do not stand that menu up for one control, revisit when there is a real reason to open it.

  4. Hold the line on accent color. Text size might one day earn an Accessibility tab. A color picker earns nothing. The accent is the one piece of color this system spends, and Appearance is not where we spend it.
