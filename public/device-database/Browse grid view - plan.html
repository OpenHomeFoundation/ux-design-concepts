Planning · Stage 02 increment

Browse grid view: a second way to look, not a second list

Browse ships as a list, dense and scannable, one row per device. The grid view adds a photo-forward layout and a list-or-grid toggle, for the moments when you are shopping by eye rather than reading specs. It is a display option over the exact same filtered set. This is the plan for keeping it a view, and never letting it become a different answer.

Builds on Stage 02 · Richer device pages · pairs with Photos and gallery

The grid changes how the results look, never which results they are. Same filters, same predicate, same count. The toggle is a lens on one list, not a parallel index that could drift from it. That single rule is what makes the increment safe to switch off: turn it off and Browse falls back to the list with nothing lost.

What it is

One result set, two layouts

Browse already owns the hard part: a filter model in the URL, a predicate that runs over reported fields, and a live count. The grid view sits on top of that. It reads the same filtered set and lays it out as cards that lead with the device photo, where one exists, instead of a row of text. The list stays the default and the canonical view.

Listdefault · text-forward

One row per device: name, manufacturer, the verdict, the integration. Dense, sortable by eye, best for reading and comparing facts. The view a deep link opens in.

Gridincrement · photo-forward

Cards leading with the photo where there is one, falling back to a clean text card where there is not. Best for browsing by shape and recognising a box you have seen.

With the increment off, Browse forces the list and hides the toggle entirely, so there is no dead control pointing at a view that does not exist. The chosen layout is a display preference, never a filter, so it never appears in the count or the shareable URL's result meaning.

The dependency

Independent of photos, better with them

Grid view and Photos and gallery are separate increments, and each works without the other. The grid does not require a photo: a device with none gets a text-forward card, the same facts in a different frame. But the two compound, a photo-led grid is the layout photos were collected for. They are designed to be shipped and judged separately, then to reinforce each other when both are on.

Where we draw the line

A view, held to the list's honesty

The count never changes with the layout. Grid and list show the same set. The number you see is the number you land on, in either view, same as Foundation's search.

The list stays canonical. It is the default and the fallback. A deep link, a screen reader, and the increment-off state all land on the list.

A missing photo is not a missing device. No photo means a text card, never a hidden or down-ranked result. The grid never sorts by whether a picture exists.

The card leads with facts, not flourish. A grid card carries the verdict and the integration like the row does. The photo helps you recognise it, it does not replace the answer.

Recommendation

What to hold

  1. Keep it a pure view. No grid-only filters, no grid-only ordering. The moment the layout changes the result, it has stopped being a view and started being a second, driftable index.

  2. Default to the list, fall back to it. Remember the user's choice, but treat the list as canonical so deep links and the off state are always coherent.

  3. Ship before photos, judge with photos. The grid stands alone on text cards. Its real payoff arrives when the photos increment fills the cards, so evaluate the pair together.
