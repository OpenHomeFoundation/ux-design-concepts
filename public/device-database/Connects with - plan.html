Connects with: the same device, in every house it lives in

Home Assistant is home turf, but a device rarely lives there alone. The same plug answers to Alexa, Apple Home, and Google Home too. This increment widens the Connects with section from one ecosystem to one tab per ecosystem the device is marked compatible with, each with the same three fields so the tabs stay comparable. This is the plan for that, and the line that keeps Home Assistant first.

Builds on Stage 02 · Richer device pages · data in data.js · connects-with.jsx

One device, many ecosystems, one fixed shape. Every tab answers the same three questions, how you set it up, what it cannot do there, and where the documentation lives, so a reader compares apples to apples across Alexa, Apple Home, and the rest. With the increment off, the section is Home Assistant alone, exactly the Foundation view. Turning it on adds the other rooms of the house, it never changes the Home Assistant one.

What it is

A tab per compatible ecosystem, a fixed three fields each

Six ecosystems can earn a tab: Home Assistant, Amazon Alexa, Apple Home, Google Home, Homey, and SmartThings. A device shows a tab for each one it is marked compatible with. Every tab carries the same three contributor fields, each an override over a sensible default, so an unfilled tab still reads instead of going blank.

// Six known ecosystems can earn a tab, in display order. Home Assistant first. CONNECTS_WITH_ECOSYSTEMS = ["homeAssistant", "amazonAlexa", "appleHome", "googleHome", "homey", "smartThings"] // Every tab, the same three fields. Each is an override over a default. tab { setup, limitations, documentation } // The Home Assistant tab additionally exposes integration + entity types.

The fixed-field model is the whole trick. Because every ecosystem speaks the same three fields, the tabs are genuinely comparable, and a contributor filling in Alexa knows exactly what to write. The Home Assistant tab is the one exception, it also carries the reported integration and entity types, because that is the data Foundation already holds.

The fallback

Off is the Foundation view, exactly

With the increment off, the section collapses to Home Assistant only, with no tab bar, and the heading carries the ecosystem name instead of a switcher. That is precisely the Stage 01 view: the reported integration, entity types, and documentation, with no other ecosystems and no contributor setup prose. The increment is purely additive, so toggling it never disturbs the baseline.

Where we draw the line

A compatibility map, never an endorsement

Home Assistant is always first. It leads the tab order and is the one tab that exists for every device. The other ecosystems are added context, not equals jostling for the top slot.

Only the six known ecosystems earn a tab. The free "others" list stays a list. A tab is a promise of the three structured fields, so it is reserved for ecosystems we model.

Every field is an override over a default. An unfilled tab reads sensibly rather than blank, and a contributor improves on the default rather than starting from nothing.

A tab states facts, including the bad ones. The limitations field is not optional politeness, it is where "Alexa cannot do scenes for this device" gets said plainly. Compatibility is described, never sold.

Recommendation

What to hold

  1. Keep the field shape fixed. Setup, limitations, documentation, the same three on every tab. The comparability is the feature. Per-ecosystem custom fields would quietly destroy it.

  2. Lead with Home Assistant, always. Order and primacy are not cosmetic. They state what this database is for, and the off state must equal the Foundation view exactly.

  3. Hold the tab bar to the six. Resist promoting an "other" into a tab without modelling it. The list is the right home for the long tail.
