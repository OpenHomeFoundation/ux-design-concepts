Open Home Foundation A field guide for contributors

The Device Database, explained.

Manufacturer specs say what a device should do. The Device Database records what it actually does, built from anonymized data shared by the community and enriched by people who run the hardware. This is the wiki: how the project is designed, how it is built, and how you can help shape it. Use the left rail to move between this overview and the roadmap plans.

01

What the Device Database is

A free, open reference for how smart-home devices behave in the real world, run by the non-profit stewards of Home Assistant.

Home Assistant users opt in to share which devices they run and how those devices behave. Reports are anonymized, with no personal data, no identifiers, and no addresses. The database aggregates and deduplicates those reports, pairs them with manufacturer documentation, and cross-checks them against integration source code before anything goes live.

Anyone can look a device up, no account needed. You do not have to use Home Assistant to benefit. The goal is a reference you can cite when deciding what to buy, not a marketing surface.

What an entry answers

  • Does it require an internet connection, and when (setup only, or always)?
  • Which Home Assistant integration controls it, and is that integration official or community?
  • Which protocols and ecosystems does it speak (Matter, Thread, Zigbee, Z-Wave, Wi-Fi)?
  • How many people have run it successfully, and how recently was it verified?

Where a claim is unverified, the entry says so. Where a device behaves one way on one firmware and differently on another, both are noted.

02

Design rationale

The visual language is deliberately quiet. "Less, but better." Color is signal, not decoration. The grid and the hairline carry the structure.

i.

Functional, not decorative

Graphite ink on warm paper. A single blue accent marks links and the one live or active thing on a screen. Errors and warnings keep their own red and amber. No gradients, no shadows beyond a 1px hairline.

ii.

Hierarchy by weight and size

Two typefaces do the work. Inter Tight for headings, Inter for body and UI. JetBrains Mono for IDs, hex values, and raw protocol identifiers.

iii.

The hairline carries the weight

One elevation level. Surfaces separate with a 1px border, not a drop shadow. A strict 4px grid, with 8px increments preferred. The default radius is 2px.

Color

Color is meaning. Neutrals are warm-paper biased. The blue accent does two jobs: it marks links, and it marks the one thing on a screen that is live or needs attention. It is never a decorative flourish. Errors and warnings keep their own red and amber, so a live signal is never confused with a problem.

Tokens carry semantic names, never raw hex, so the full dark theme is a single override block. Pages that use tokens correctly adapt with no extra work. See tokens.css.

Links

Links come in two kinds, told apart by one question: is the link sitting inside running text?

Inline links sit next to words, inside a sentence or a data row. They carry an underline at rest so they read as links within the text, and they turn blue on hover.

Structural links stand on their own, or in a group where the context already reads as clickable: cards, navigation, footers, breadcrumbs, standalone calls to action, the logo, a manufacturer name. They have no underline at rest, and reveal blue plus an underline on hover.

Buttons and toggles are not links. They never underline, and they darken to ink on hover rather than turning blue.

The rule is applied per element rather than auto-detected, so a bare new link follows the structural default until it is given the inline treatment. See the link rules in app.css.

Verbs over adjectives is a type decision as much as an editorial one. Numbers, model IDs, and protocol tokens are always set in mono so they read as data.

Measure

Running prose is held to a fixed measure of about 62 characters per line, no matter how wide its container is. Headings, figures, tables, and cards fill the column. Body paragraphs do not. So a paragraph often stops short of the right edge that the elements around it reach, and that is deliberate.

This is "less, but better" applied to reading. The line is sized for the eye, not the box. A short, even measure keeps the reader from losing their place on the return sweep to the next line, which is exactly where long lines get tiring. The slightly shorter right edge on paragraphs is intentional rhythm, not a misalignment to be filled in.

The cap lives on the text, not the layout, so wide columns can still carry full-width structure. See max-width: 62ch on prose in app.css.

04

Data model

A record has a read-only core and a set of fields contributors maintain. Two shifts are documented here: data reaches a record three ways, not two, and Stage 04 grows the unit from a single device to a family of variants.

Three ways data enters a record

A record is not built only by people. Most of what the database publishes arrives without anyone writing prose, which is what lets coverage keep pace with the catalogue.

i.

Observed

Gathered automatically from anonymized Home Assistant reports: identity, the local and cloud posture, the controlling integration, entity types, and the counts. Nobody writes these, they reflect what the telemetry sees.

ii.

Mapped

Matched to a record by an identity key, an FCC ID, a Z-Wave product triple, a Zigbee model string, or a printed model code, with no contribution required. This is how coverage grows with the dataset rather than only with volunteers.

iii.

Authored

The written half: description, instructions, structured specs, references, and per-ecosystem notes. Proposed, reviewed, and attributed before it goes live.

The first two arrive without anyone writing prose. A device can hold a truthful, useful record before a single contributor touches it. Authoring deepens a record, it is not the only way one exists.

Families and variants

Proposed · Stage 04

One product on a shelf can hide several genuinely different devices. A Yale lock takes a Z-Wave, a Matter, or a Wi-Fi module, and whether it works without the cloud changes with the module. A plug sold worldwide runs at 120 V here and 230 V there. So the unit grows from a device to a family of variants.

A family holds shared truth once. Under it sits an enumerated list of variant rows, and each row is a first-class, addressable record with its own verdict, identity keys, and telemetry. This matches what every runtime database that has to recognise real hardware (zwave-js, Zigbee2MQTT) converged on independently: enumerated rows keyed on identifiers, not a computed grid.

Axes are derived, not authored

An axis is a dimension a family varies along: protocol, region, hardware revision, power source, and others. Axes are read off the variant rows, not entered as a fixed schema, because different families vary on different things and roughly a third do not factor into a clean grid at all.

The switcher and the verdict matrix on a device page are views generated from the rows. They only ever offer combinations that shipped, so a buyer cannot land on a variant that never existed. When a family does not factor, the same rows render as a plain list.

family.recordSchema · proposed, trimmed
// ── Family: shared truth, written once ───────────────
id:       "yale-assure-lock-2",
shared:   { description, photos, dimensions },   // never copied per variant
axes:     { protocol: ["zwave","matter","wifi"], region: ["us","eu"] },  // derived from the rows

// ── Variants: an enumerated list. Each row is its own ────
// ── first-class record: its own URL, verdict, telemetry. ─
variants: [
  {
    id:      "yale-assure-lock-2.us-zwave",
    verdict: { local: "always", cloud: "none", integration: "Z-Wave JS",
               firmware: ">= 1.83.0",            // the claim is scoped to firmware
               lastVerified: "2026-04-01" },
    region:  { mains: "120 V / 60 Hz", rfBand: "908.4 MHz", plug: "-" },  // power binds to region
    match:   { fccId: "M5GYRD420", zwave: "0x0129:0x0001:0x0001",
               printedModel: "YRD420-ZW2-619" },  // identity keys, the Mapped path
    reports: 904, installs: 712                    // scoped to this variant, never pooled
  },
  /* …us-matter, eu-zwave, eu-matter: only combinations that shipped */
]

Identity keys, the match index

Identity keys move from a buried spec field to a first-class index, because they are what makes the Mapped path work and what tells two variants apart. A variant carries as many as it has: FCC ID, the Z-Wave product triple, the Zigbee model string, the printed model code, and the hardware revision. This matters because the box often cannot disambiguate on its own. A Zigbee model string is only visible after pairing, and white-label hardware is not identifiable from the outside at all, so recording the key is a service the database provides that the packaging does not.

Correctness rules

These rails hold the model honest. They are the places the database refuses the convenient answer.

  • A verdict is scoped to a firmware range and a last-verified date. Firmware is the one thing that flips local versus cloud with no purchasable difference: a Kasa update kept local control but added an account requirement, an Eve upgrade moved a device from HomeKit to Matter. Firmware is not a variant you can buy, so it qualifies the verdict rather than splitting the record.
  • Region is not one axis. It decomposes into RF band, mains voltage, plug type, certification, and cloud-server region. Australia proves the point: 230 V like the EU, but 921 MHz, unlike it. A single region enum would misstate one fact or the other.
  • Power is bound to region, and never shown without one. A family page resolves a region before it prints a voltage or a plug. We would rather show nothing than show the wrong region's electrics.
  • Telemetry is scoped to the variant. Reports never pool across a family. A Z-Wave lock's reports do not bleed onto the Wi-Fi variant that behaves nothing like it, even at the cost of headline volume.

Category-aware specs

The structured spec fields are not a fixed list. CATEGORY_SPECS maps each device category to the fields that make sense for it, and tells the editor which control to render. Edit mode shows the right input, read mode shows only the fields that have a value.

05

Frontend architecture

A React application with no build step in the prototype: components load as plain global scripts, share state through a small client API, and feature work ships as toggleable increments.

The app

React with hash routing. The root parses the route and renders one page component. Shared UI (the nav, footer, badges, the device card) lives in a shared module and is exported onto a single global namespace so other scripts can reuse it without a bundler.

Each script tag owns its own scope. Components that need to cross files are attached to the window namespace at the end of their file, which keeps the prototype buildless and the source directly readable.

Increments and stages

Features are built as increments grouped under stages. Foundation is the baseline (browse and read). Richer device pages comes next, then accounts and editing, each building on the last. Two further stages, variants and families and goal-based discovery, are planned.

Increments sit under a stage and are independent of one another. Richer device pages carries the grid view, photos, and the per-ecosystem Connects with. Accounts and editing carries contributor profiles, notifications, and Your edits. An increment is gated by a data attribute on the root element, and turning a stage on also turns on what it depends upon, so the team can preview the next iteration without branching the whole app.

Client-side APIs

The frontend exposes two small contracts. These are the seams a contributor or developer touches first.

Theming

A small boot script resolves the effective theme before first paint, from an explicit saved choice or the operating-system preference, and writes the result to the root element. The full light and dark themes are expressed entirely through the design tokens, so no component carries its own color logic.

06

Backend and APIs

Today the prototype has no server. This section is honest about what exists now, then proposes the service the project will need as contribution scales.

Today, in the prototype

No backend. The reference ships as a static bundle. The device dataset is a JavaScript file loaded with the page.

Contributor actions (edits, sign-in, notifications, profile changes) are simulated against the browser's local storage, the "demo stores." They survive a refresh and can be reset, but nothing leaves the device.

Edit submissions render as if a pull request were opened, and the Your edits dashboard links out to GitHub, but no live request is made. This keeps the prototype fully explorable offline.

Proposed, for production

A read API plus a contribution service. A cached, public read layer serves device records to the static frontend. Telemetry ingestion writes the core fields on a schedule.

Contributor edits are validated, then committed as pull requests against the data repository. Review and merge happen in GitHub, the source of truth stays in version control.

Authentication is delegated (GitHub, plus email). The frontend stays static and cacheable, the write path is the only stateful service.

Proposed endpoints

A sketch, not a commitment. Read endpoints are public and cacheable. Write endpoints require a session and always produce a reviewable pull request, never a direct write to live data.

07

Contribution workflow

Editing happens in place, on the device page. Every change becomes a reviewable pull request, attributed to you, and only goes live once a maintainer merges it.

01

Edit in place

Sign in, open a device, and edit a field directly on the page. No separate form.

02

Submit

The change is packaged with your attribution and a summary of what moved.

03

Pull request

A pull request opens against the data repository. The field locks with an "awaiting approval" state.

04

Review

A maintainer checks the change against sources, discusses on GitHub, and merges or declines.

05

Live

On merge, the field updates, your contribution is recorded, and you are notified.

If you are not a developer

You do not need to know Git. Click a field, change it, and submit. The site handles the rest.

While your change waits, the field shows who submitted it and that it is awaiting approval, so nobody edits over you.

When a maintainer merges it, the page updates and you are notified, with the change shown as live on Your edits. If something needs discussion, the conversation happens on the linked pull request.

Developer detail

Edits map to fields on the device record. A submission opens a PR against OpenHomeFoundation/device-database and carries a numeric PR id.

Notifications are one event model surfaced in two places: the Settings notifications panel (channel and cadence) and the Your edits dashboard, which reads the records directly. Each event is typed (pr for awaiting approval, live for merged, declined for sent back) and links to the PR. The standalone nav inbox popover was retired when Your edits shipped, so the nav icon now opens that dashboard.

Attribution is first-class. Edit history and contributor profiles read from the same records, so credit follows the change through review to merge.

Review states

A field is always in exactly one of these. The state is visible on the page, so the database never silently shows an unreviewed claim.

Live Awaiting approval Seen

The folder rail

Your edits opens on Drafts when you have any, since that is where you act, and otherwise on Submitted. Drafts are unsubmitted and account-only, a different class from the GitHub-tracked states, so they never roll up into Submitted. Under Submitted sit the three lifecycle states, each shown only when you have something in it.

Drafts · your move

Draft. An edit you started but have not submitted. The row opens straight back into edit mode, and "Submit all" batches every draft into one pull request per device.

Submitted · tracked on GitHub

Awaiting review. Submitted, a pull request is open. The row shows the comment count and opens the PR.

Live. Merged and public. The row links to the device page.

Declined. Not accepted. You can revise it, which reopens the edit on the device.

Every submitted row carries a status badge, and where the review has discussion, a comment count read from the pull request (the PR_COMMENTS seam in data.js that the GitHub API would later fill). Opening a submitted row leaves the site for the pull request, since that is where the change and its status live.

Planned: a computed "Needs you"

Today the rail sorts by lifecycle state. A planned refinement adds a single "Needs you" signal that separates edits waiting on a reviewer from edits waiting on you. It would never be assigned by hand. It would be read from the pull request, so it stays trustworthy instead of crying wolf. The data seam is already in place: each PR record can mark its latest comment as an unanswered reviewer question (unanswered in PR_COMMENTS).

Needs you · your move

Declined. The PR was closed without merging. Revise and resubmit.

Changes requested. A reviewer filed a formal request for changes.

Unanswered comment. The newest activity is a reviewer's question, after your last reply or commit.

Cannot merge. A conflict, or a failing required check on your branch.

Awaiting approval · reviewer's move

Not yet reviewed. Submitted, nobody has looked.

You already responded. You replied or pushed a commit, so it is back with the reviewers.

Approved and queued. Accepted, waiting to merge.

A pending change sits in exactly one camp at a time.

The flag would be evaluated in order of precedence. The first match wins, and each condition is read from the pull request itself, not from anything a person sets.

#ConditionRead from the pull request
1Declinedstate = closed, not merged
2Changes requestedreviewDecision = changes_requested. The clean, unambiguous trigger
3Unanswered commentlastReviewerActivity > lastYourActivity
4Cannot mergemergeable = false, or a failing required check

Hard versus soft. Declined and changes-requested are authoritative and would earn the full treatment. A bare unanswered comment is softer, a reviewer may just be remarking, so it would show as the amber comment count alone and escalate to the full "Needs you" flag only on a formal changes-requested.

Editorial stance and voice

Neutral, citable, never sponsored. We list what a device does, not what we think about it. Trust is built by being honest about gaps.

The Device Database is a reference, not a marketing surface. There are no sponsored placements and no recommendation rankings. If a device requires the cloud, we say so plainly. If a claim is unverified, we mark it.

Write this way
"The sensor reports presence using mmWave radar."
"Exposes 14 entities."
"Reported to work, unverified."
Not this way
"This is a great presence sensor."
"Powerful entity support."
"Works perfectly, trust us."

Verbs over adjectives. Acknowledge uncertainty explicitly. Entries are written in the voice of a wiki editor: declarative, source-backed, and explicit about what is not yet known.

Glossary

Terms that recur across the project, the database, and this wiki.

Core fields
The read-only half of a device record, derived from anonymized telemetry. Identity, local and cloud posture, integration, entity types, and counts. Contributors do not edit these.
Contributor fields
The editable half: description, instructions, structured specs, references, and per-ecosystem setup notes. Every change is reviewed before going live.
Local posture
Whether a device works without the cloud: always, sometimes, or never. The single most important fact in most entries.
Increment
A unit of feature work, gated behind a flag so it can be previewed in isolation. Increments group under stages and build on one another.
Stage
A milestone that bundles related increments. Foundation, then richer device pages, then accounts and editing, with variants and families and goal-based discovery planned.
Category specs
The per-category set of structured spec fields, each with a control type. Defines what the editor shows for a camera versus a thermostat.
Pull request (PR)
The reviewable change a contributor edit produces, opened against the data repository. The unit of review and the source of attribution.
Integration
The Home Assistant component that controls a device. Marked official, community, partial, or none, with a link to its documentation where one exists.
Connects with
Per-ecosystem setup guidance (Home Assistant, Apple Home, and others), derived from a device's protocols and editable by contributors.
Family
A product line that hides more than one device, holding the shared truth (description, photos, dimensions) once. Under it sit the variants.
Variant
One genuinely different device within a family, stored as an enumerated row with its own URL, verdict, identity keys, and telemetry. A difference earns a variant only when it changes a buying fact.
Axis
A dimension a family varies along: protocol, region, hardware revision, power source, and others. Axes are derived from the variant rows, not authored as a fixed schema.
Identity key
A machine-readable identifier that pins a record to real hardware: FCC ID, Z-Wave product triple, Zigbee model string, printed model code, hardware revision. The basis of the Mapped data path.
Verdict
The local-versus-cloud claim for one variant, scoped to a firmware range and a last-verified date so it stays true as firmware changes behaviour.
Data paths
The three ways data reaches a record: observed (from telemetry), mapped (matched by identity key, no contribution), and authored (written and reviewed).
Token
A named design value (color, type, spacing). Components reference tokens, never raw values, which is what makes theming a single override.
