Planning · Stage 01

Foundation: the floor every stage stands on

The whole project answers one question about a smart-home device: does it work locally with Home Assistant, and how. Foundation is the smallest honest thing that answers it, browse, search, and read, built from data the community opts in to share, with no account needed and no personal data collected. This is the plan for what the baseline holds, and what it deliberately does not.

The floor that Stages 02–05 all build on · sets the line held by the editorial stance

Foundation is not a feature. It is the contract. It fixes three things the rest of the roadmap inherits and never renegotiates: where the data comes from (opt-in, anonymized), the single fact the database exists to publish (the local-or-cloud verdict), and who is allowed to read it (anyone, no account). Get these right once and every later stage is an addition. Get them wrong and there is nothing honest to build on.

The source · where the facts come from

Opt-in, anonymized, and that is the whole point

Manufacturer specs say what a device should do. Foundation tracks what it actually does, assembled from Home Assistant users who choose to share which devices they run and how those devices behave. The chain is three steps, and each one is a constraint, not a convenience.

The community sharesopt-in · anonymized

Users opt in to report what devices they run and how they behave. No personal data, no identifiers, no addresses. The privacy line is load-bearing, not a footnote.

The database verifiesdeduplicated · cross-checked

Reports are deduplicated, paired with manufacturer documentation, and cross-checked against integration source code before a fact goes live.

No personal data is the rule the rest of the project is shaped around. Counts like reports and installs are aggregate signal, never a list of people. Stage 03 later adds named contributor accounts, but those describe who edited an entry, never who runs a device. The reporting population stays anonymous forever. That separation is decided here so no later stage has to walk it back.

The record · what an entry actually holds

Reported facts, and nothing that needs an editor

A Foundation entry is the set of fields a report can justify on its own. It identifies the device, names how Home Assistant talks to it, states the verdict, and carries the aggregate counts and the version history that catches change over time. Everything that takes an editor to write, the curated overview, references, requirements, detailed specs, belongs to Stage 02, not here.

// A Foundation entry: facts a report can stand behind by itself. { id, name, manufacturer, model, category, // identity local: "always" | "sometimes" | "never", // the verdict, three axes cloud: "none" | "optional" | "required", ha: "official" | "community" | "partial" | "none", haIntegration, // what controls it reports, installs, // aggregate signal, never people entityTypes, protocols, identifiers, // reported, not narrated versionHistory, firstSeen, lastVerified // change over time } // summary, references, requirements, detailed specs → Stage 02 enrichment

The seam matters because search and Browse are built to read only the reported fields. A committed search never matches on the Stage 02 summary, so the baseline can never surface a device on enrichment text it does not otherwise show. Foundation stays self-contained: it does not reach forward into a stage that may be switched off.

The verdict · the one fact worth the project

Three axes that resolve to one answer

"Does it work locally" is not a yes-or-no. A device can run fully on the local network, lean on the cloud for some features, or refuse to work without an account. Foundation pins that down with a fixed, three-axis vocabulary so every entry answers in the same words and a reader learns to read them once.

The verdict is reported, never editorialized. The entry states "runs locally over Zigbee, cloud optional," not "a great local bulb." Where a claim is unverified, the entry says so. Where a device behaves one way on one firmware and another way on the next, both are noted, and that is exactly what versionHistory exists to hold. Change over time lives here, not in a variant.

The surfaces · three doors, no key

Browse, search, read, and never a sign-in wall

Foundation ships three ways into the same facts, and all three work for a visitor who has never heard of Home Assistant. You do not have to run it to benefit, and you never have to make an account to look something up. That is a deliberate floor: reading is always free and open.

Browsebrowse.jsx · filter on reported fields

The filterable index. Every filter, category, protocol, the local-or-cloud verdict, runs against reported fields, so the count you see is the count you land on.

Searchsearchbox.jsx · self-contained corpus

A word index built only from reported fields: names, manufacturers, models, categories. Six quick-filter recipes give a zero-typing on-ramp into Browse.

The device page is the third door: the read view of one entry, showing the verdict, the integration, and how many others have run it. Stage 02 enriches that page, Stage 03 lets a signed-in member edit it, but the bare, account-free read is Foundation, and it is what the others decorate.

Where we draw the line

What the baseline refuses, on purpose

The editorial stance is neutral, citable, never sponsored. Foundation is where those words become rules in the data, not aspirations in a footer. These rails hold under every stage above.

Data is opt-in and anonymized, always. The reporting population is never named, never located, never counted as people. Aggregate signal only. No later stage relaxes this.

Reading needs no account. Sign-in arrives in Stage 03 for editing, never for looking something up. The lookup is free and open to anyone.

Search reads only reported facts. The corpus is names, models, and categories, never the Stage 02 summary, so the baseline can never surface a device on text it does not show.

The verdict is stated, not graded. "Runs locally, cloud optional," not "best local bulb." No ranking, no affiliate, no recommendation order. Verbs over adjectives.

Recommendation

What to protect, in order

  1. Keep Foundation small. The temptation is to pull an enrichment field forward because it is useful. Resist it. A field belongs in the baseline only if a single report can justify it without an editor.

  2. Hold the reported-versus-enriched seam. Search and Browse read reported fields only. Every stage that adds narration must leave that corpus alone, so a toggled-off stage never changes what the baseline finds.

  3. Never trade the privacy line for a feature. The opt-in, anonymized, aggregate-only rule is the project's credibility. Anything that would name or locate the reporting population is out, no matter how much it would add.

  4. Keep reading account-free, forever. Stage 03 may gate editing behind sign-in. The lookup never moves behind a wall, that openness is the reason the database is worth keeping.
