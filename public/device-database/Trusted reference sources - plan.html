Planning · Stage 03 increment

Trusted sources: the same front door for outside data

When a device matches a source we trust, recognised by its own model or EAN, we should offer what that source knows to contributors. Not paste it in. The plan is to bring outside data through exactly the path every other edit takes: proposed, attributed, and reviewed on GitHub before it goes live.

Builds on Stage 03 · Accounts and editing · reuses the pending-review model in pending-edits.jsx and the editorial stance

This is an increment, not a new stage. Half of it is already in the codebase, dormant. Edit mode was built to accept a makeSuggest function, every field editor already renders a suggestion rail with an Apply button, and the pending store already records a source per field. What is missing is small: a data layer that recognises a device by its identifiers, one notice in the sidebar, and the wire that connects them. The review bar does not move an inch.

The data layer

A source recognises a device by its identifiers

This is the reason the increment exists. A source declares how it recognises a device, by model or EAN, and carries an index keyed on that identifier. A device resolves its matches from its own identifiers, so nothing is hand-listed per device and coverage grows as the dataset does. Keep it in the dataset, never inline in a component, so the notice, the suggestions, and the attribution all read from one place.

// window.TRUSTED_SOURCES — each source says how it recognises a device { id: "zigbee2mqtt", name: "Zigbee2MQTT devices", reviewPolicy:"contributor-review", // requires a human pass matchOn: ["model", "modelId"], // recognise by identifier deviceLink: (d) => `https://www.zigbee2mqtt.io/devices/${d.model}.html` } // Each source carries an index keyed by the identifier it matches on. // A device resolves its matches from its own model / EAN — no per-device list. matchesFor(device) → [ { source, fields: { protocols, identifiers, … } }, … ]

The field keys are the ones the pending store and editors already speak: protocols, identifiers, ecosystems, dimensions, references, and the rest of contributorFieldKeys. A source can only ever propose fields a contributor is allowed to edit, never the read-only Home Assistant core.

The visitor path

One notice, then the suggestion rail

On a device known at one or more trusted sources, a notice appears in the sidebar above Real-world data. If several sources match, they bundle into a single notice, never one box per source. The notice says additional data is available and offers one call to action: add it as a reference.

The call to action opens edit mode with makeSuggest supplied. From there the already-built rail takes over, and the contributor decides every value. The one design decision worth getting right is how source data meets data the page already has.

SituationWhat the contributor sees
Sources agree on a value Shown once, a single suggestion with an Apply button.
Sources disagree Shown as separate suggestions, one per source, each with its own Apply. The contributor picks.
Field has no existing value Suggestion shown, input left empty. Nothing is pre-filled. Apply fills it.
Source conflicts with an existing value Per-field suggestion sits beside the current value. Apply replaces it, the contributor confirms.

One rule unifies the table: the source never silently writes an input. Every value is a proposal the contributor applies. That is exactly what the dormant SuggestionRow already does, which is why this is wiring and not new interaction design.

Where we draw the line

Trusted to surface, never trusted to write

The editorial stance is neutral, citable, never sponsored. A trusted source is a convenience, not an authority. These rails hold throughout.

A source proposes, a contributor decides. Nothing from a source writes a field unattended. Apply is always a human action, and the submit still goes to review.

The source is named, always. Every value that came from a source carries that source into the pending entry, the attribution, and the edit history. Provenance is not optional.

The read view never changes from a source alone. Until an edit is reviewed and merged, the page shows the last approved data. A match adds a notice, never a value.

Conflicts are shown, not resolved for the contributor. When sources disagree, both are offered. The database does not pick a winner on a visitor's behalf.

Recommendation

What to do, in order

  1. Ship it as one increment on Stage 03, one toggle. It reuses the entire edit-and-review machinery and depends only on community-edit, never on another increment. A new stage would overstate it, and splitting it into separate toggles would couple increments to each other.

  2. Match on the identifier, not a hand-listed map. Recognising a device by its model or EAN is the reason the feature exists. It is what lets coverage grow with the dataset instead of one entry at a time.

  3. Treat the conflict semantics as the one design problem. Agree once, disagree twice, empty without pre-fill, conflict beside the current value. That is where a helpful rail and a noisy one diverge. The rest is connecting seams that already exist.

  4. Register it on the canvas beside Profiles and Notifications. Add trusted-sources under Stage 03 in canvas.html and the index boot deps, so the roadmap shows the third Stage 03 child.
