Planning · Stage 03 increment

Your edits: one place for what you have in flight

A contributor used to track their work across two surfaces, a notifications inbox and a changes tray. This increment merges them into one private dashboard that answers a single question: what have I got in flight, and what happened to it? Drafts, edits in review, what went live, what was declined, with submit-all batching. This is the plan, and the reason it replaces the tray rather than joining it.

Builds on Stage 03 · Accounts and editing · lives in your-changes.jsx · replaces the Changes tray

One question, one surface. Drafts, pending review, live, declined: a contributor wants all of it in a single view they can reach from one nav icon, not split between a tray for things going out and an inbox for things coming back. Your edits merges those into an inbox-shaped dashboard, and retires the changes tray so there is exactly one home for a contributor's in-flight work.

What it is

An inbox for your own work

The layout is an inbox. A left folder rail leads with Drafts, where you act, then a hairline, then the submitted lifecycle: All, Awaiting approval, Live, Declined, each with a count. Drafts are unsubmitted and account-only, a different class from the GitHub-tracked states, so the submitted folder never counts them. The page opens on Drafts when you have any, otherwise on the submitted view.

A row click goes where the work lives: a draft opens straight into edit mode, since no pull request exists yet, and a submitted change opens its pull request, since that is where the change and its status are. On tablet the rail becomes a tab strip, and on mobile the table becomes cards.

The one new mechanic

Submit all, one pull request per device

Most of the dashboard is a clear view over states that already exist. The one genuinely new action is batching: Submit all takes every draft and opens one pull request per device. That is the right grain, because a device page is the unit a reviewer reviews and the unit that merges, so a contributor who has been tidying ten devices sends ten reviewable changes, not one tangled mega-edit and not ten separate clicks.

Where we draw the line

Private, honest about state, one home

Drafts are account-only, never public. An unsubmitted draft is a private class, kept out of the submitted counts and off your public profile until it becomes a pull request.

One device, one pull request. Submit-all batches by device because the device page is what a reviewer reviews. It never bundles unrelated devices into one unreviewable change.

Declined is a beginning, not a wall. A declined edit can be revised and resubmitted from here. The dashboard treats it as work to continue, not a failure to file away.

One home, so retire the tray. Merging means actually removing the changes tray, not running both. Two surfaces for in-flight work is the problem this increment exists to end.

Recommendation

What to hold

  1. Keep drafts a separate class. Account-only, never in the submitted counts, never public until submitted. Blurring drafts into pending is how a private workspace leaks.

  2. Batch by device, always. One pull request per device matches what review and merge operate on. Resist a single combined PR, and resist making the contributor click through one at a time.

  3. Actually replace the tray. The win is one surface. Shipping Your edits while leaving the tray in place would recreate the very split it set out to fix.
